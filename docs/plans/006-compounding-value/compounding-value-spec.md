# Compounding Value — Difficulty Ledger, Velocity Tracking & Philosophy

**Mode**: Simple

📚 This specification incorporates findings from `workshops/001-compounding-value-in-minih.md`

## Summary

minih already has the core self-improvement loop — magic wand → fix → verify. But it doesn't **measure** or **surface** the compounding effect. Users can't see that their harness investment is paying off, agents can't report structured friction, and velocity trends are invisible.

This feature adds three capabilities that make the compounding value loop visible, measurable, and actionable:

1. **Difficulty Ledger** — agents report structured friction (`retrospective.difficulties`), minih aggregates it (`minih difficulties`), resolved items feed back to agents via the preamble
2. **Velocity Tracking** — per-agent velocity data stored in `completed.json`, surfaced in `minih history` as trend indicators
3. **Philosophy & Docs** — weave the experiment's key framings ("every task sends a gift to its future self", "encode don't document", "the maturity curve") into AGENTS_README, preamble, and SYSTEM_OUTPUT_INSTRUCTIONS

**WHY**: The velocity experiment proved 64× improvement across 5 iterations on the same codebase. minih is the engine that powers this loop — but today it doesn't surface the evidence. Users should be able to see the curve, agents should be able to report the friction that's slowing it, and the docs should articulate why this matters.

## Goals

- Agents can report structured difficulties with category, description, workaround, and severity
- Humans can see all difficulties across all agents in a single view (`minih difficulties`)
- Known/mitigated difficulties are visible to agents on startup (preamble)
- Velocity data (change vs previous run, overall trend) is computed and stored per-agent
- `minih history` shows velocity trends (faster/slower vs previous run)
- The magic wand target (project vs minih) is explicit in the schema, not just prose
- AGENTS_README and preamble articulate the compounding value philosophy with the experiment's best framings
- Agents are prompted to report difficulties in SYSTEM_OUTPUT_INSTRUCTIONS

## Non-Goals

- No "value axis" measurement — quality of output is inherently qualitative, stays in `summary`
- No automated difficulty-to-fix pipeline — humans curate the preamble manually
- No magic wand maturity auto-classification — the maturity curve is a teaching concept, not a feature
- No cross-agent velocity comparison — velocity trends are per-slug only
- No dashboard or visualization — `minih difficulties` and `minih history` are CLI tools, not a web UI
- No changes to how agents run — this is data capture, surfacing, and documentation

## Target Domains

| Domain | Status | Relationship | Role in This Feature |
|--------|--------|-------------|---------------------|
| runner | existing | **modify** | Store velocity block in completed.json, update SYSTEM_OUTPUT_INSTRUCTIONS, update retrospective schema |

No new domains. This feature enriches existing domains with new data capture and surfacing.

## Complexity

- **Score**: CS-3 (medium)
- **Breakdown**: S=2, I=0, D=1, N=0, F=0, T=1 → Total P=4 → CS-2/CS-3 boundary
- **Confidence**: 0.85
- **Assumptions**:
  - Difficulty categories are freeform strings with suggested defaults (not enums)
  - MH- IDs are auto-generated by `minih difficulties` aggregation
  - Velocity block is computed at run completion time by reading previous completed.json files
  - Philosophy/doc changes are straightforward text edits
- **Dependencies**: None — all internal to minih
- **Risks**:
  - Velocity computation needs to scan previous run folders (could be slow with hundreds of runs — mitigate by only reading last completed.json)
  - Schema changes must be backward compatible (all new fields optional)
  - Agents with inlined retrospective schemas (3 agents) need updating
- **Phases**: 3 suggested — (1) schema + velocity storage, (2) difficulties command + history enhancement, (3) philosophy docs

## Acceptance Criteria

### Schema & Data Model

- **AC1**: `retrospective.json` and `system-output.json` schemas include optional `magicWandTarget` field (string: `"project"` or `"minih"`)
- **AC2**: `retrospective.json` and `system-output.json` schemas include optional `difficulties` array with objects containing `category` (string), `description` (string), `workaround` (string or null), `severity` (string: `"blocking"`, `"degrading"`, or `"annoying"`)
- **AC3**: Existing agent outputs without the new fields still validate successfully (backward compatible)
- **AC4**: All agents with inlined retrospective schemas (code-review, convention-check, first-time-experience, feedback-digest, mcp-smoke-test, prompt-review, self-review, smoke-test — 8 total) are updated to include the new optional fields

### Velocity Tracking

- **AC5**: `completed.json` includes a `velocity` block with `previousDurationMs`, `changePercent`, `runNumber`, `firstDurationMs`, `overallChangePercent`
- **AC6**: First run for an agent has `velocity.previousDurationMs` as null and `velocity.runNumber` as 1
- **AC7**: Only completed runs are compared (failed/degraded are skipped for velocity calculation)
- **AC8**: `minih history` displays a trend column showing ▼ (faster), ▲ (slower), or — (first run / within 5% noise)
- **AC9**: `minih history` displays a velocity summary line: `Velocity: Xm Xs → Ym Ys over N runs (Z% faster)`

### Difficulty Ledger

- **AC10**: `minih difficulties` command aggregates difficulties from all agent run outputs across all agents
- **AC11**: `minih difficulties` auto-assigns MH-001, MH-002... IDs to each reported difficulty (raw aggregation, no deduplication — agents/humans curate after the fact)
- **AC12**: `minih difficulties` output shows ID, category, description, agent slug, frequency (exact-description count), severity on stderr as a table and stdout as JSON envelope. Status defaults to "open" (humans curate resolved items into preamble manually).
- **AC13**: `minih difficulties` handles the case of zero difficulties gracefully (empty table)

### Prompting & Documentation

- **AC14**: SYSTEM_OUTPUT_INSTRUCTIONS in runner.ts explains the `difficulties` array with a JSON example and instruction text
- **AC15**: SYSTEM_OUTPUT_INSTRUCTIONS mentions `magicWandTarget` with guidance on project vs minih
- **AC16**: Preamble includes a "Known Difficulties" section with a table (initially populated with minih's own known difficulties)
- **AC17**: Preamble includes "Every task must send a gift to its future self" framing
- **AC18**: Preamble includes suggested difficulty categories with note that agents can use their own
- **AC19**: AGENTS_README includes "The Core Principle" subsection with "gift to future self" language
- **AC20**: AGENTS_README includes "Encode, Don't Document" subsection
- **AC21**: AGENTS_README includes "The Maturity Curve" as a named concept
- **AC22**: AGENTS_README includes "The Difficulty Ledger" subsection explaining the A→B→C pipeline

### Run Output Surfacing

- **AC24**: The stdout JSON envelope from `minih run` includes `summary`, `magicWand`, `magicWandTarget`, and `difficulties` fields extracted from the agent's report.json (so calling agents/scripts see retrospective data immediately without reading report.json)
- **AC25**: The stderr human-readable summary displays the magic wand text and difficulty count when present

### External

- **AC23**: `harness-is-the-product-v2.md` skill (in `~/github/tools/agents/v2-commands/`) updated to reference minih-specific mechanisms (MH- IDs, `minih difficulties`, `retrospective.difficulties`, A→B→C pipeline)

## Clarifications

### Session 2026-04-14

**Q1: Workflow Mode** → **Simple Mode**. Single-phase plan, inline tasks, lighter process. Despite CS-3 scoring, the work is well-understood from the workshop and doesn't need multi-phase gates.

**Q2: Testing Strategy** → **Lightweight**. Minimal validation tests for schema backward compat and velocity computation. Manual verify for docs and CLI output.

**Q3: Mock Usage** → **Avoid mocks entirely**. Real fixture files and run folders, matching minih's existing test patterns.

**Q4: Documentation Strategy** → **AGENTS_README + preamble only**. The changes ARE the docs. No separate guide.

**Q5: Difficulty Deduplication** → **No deduplication in the command**. `minih difficulties` does raw aggregation — lists every reported difficulty as-is. Calling agents or humans can curate/tidy after the fact if it gets messy. Keeps the command simple and predictable.

**Q6: Velocity Command** → **`minih history` is sufficient**. No dedicated `minih velocity` command. Velocity data stored in `completed.json` for agents to read directly; `minih history` shows trends for humans.

**Q7: Preamble Known Difficulties** → **Manually curated**. Human reviews `minih difficulties` output, promotes resolved items to preamble's Known Difficulties table. Same pattern as the existing evidence table.

**Q8: Domain Review** → **Confirmed**. runner (modify), cli (modify), adapter (consume only). No new domains. Import direction unchanged.

**Q9: Run Output Surfacing** → **Include in stdout envelope**. Currently the JSON envelope from `minih run` only has metadata (slug, runId, durationMs, validated). The agent's actual retrospective content (summary, magicWand, difficulties) sits in `report.json` and callers have to dig for it. Resolution: extract key retrospective fields into the stdout envelope AND display magic wand + difficulty count in the stderr summary. This makes the compounding value data immediately visible to calling agents and scripts.
