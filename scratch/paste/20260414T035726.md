# We Ran a Harness Velocity Experiment — Here's What We Learned

**Author**: Jordan Knight · **Date**: April 2026

---

## The Real Problem

We have a platform that powers accounting for hundreds of thousands of Australian businesses. It's 15 years old, built on .NET Framework, with two execution stacks (one from 2008, one from 2020), multiple build systems, and six cloud service dependencies just to make a single local API call.

Here's the uncomfortable truth: **the platform is hard to work on.** Not because the code is bad — it's mature, it works, it handles real money for real businesses. But the knowledge required to be productive in it is vast, tribal, and largely undocumented. The people who built it have moved on. The feedback loop is slow. New engineers face months of ramp-up. And the ideas we want to explore — AI agent integration, new capabilities, architectural experiments — are bottlenecked by the sheer difficulty of *getting in*.

As bringers of an agentic engineering future, our job isn't to rewrite the platform. Our job is to **break down the barriers** — to create the capability to rapidly experiment and iterate on it. To make it possible to ask a question about the codebase and get an answer in hours, not weeks. To try an architectural approach, prove or disprove it, and move on.

We needed a real problem to drive the experiment. We chose audit provenance — making the system record when an AI agent (rather than a human) makes a change. That was the exercise. But the experiment was about something bigger:

> **Can we build an engineering system that makes a difficult legacy codebase accessible to rapid experimentation?**

---

## The Harness Concept

When you name a thing you make it a first class concept. This is why I think the harness concept is so powerful - its creating a campfire. We named it *the Huxley Harness* (named for the codeword of the codebase), gave it a CLI, gave it prompts and subagents, and treated it as a first-class product — not scaffolding, not a nice-to-have, not something we'd clean up later.

Why does naming it matter? Because once something has a name, you can measure it — is it getting better? You can improve it — there's one place to invest instead of ad-hoc scripts scattered across wikis. And you can talk about it. "The harness needs X" is a real conversation. "We should probably write a script for that" is a hope that dies in the backlog.

The harness is a CLI with commands like `build`, `run`, `health`, `seed`, and `test`. It automates the lifecycle of the system under experiment. It has 16 commands and 32 recipes. It eliminates cloud dependencies, automates database seeding, and lets an agent go from zero to a working API call in under two minutes.

Most imporatntly its discoverable by agents. It can be known instantly. It gives them a way to edit, build, see inside the running product. Close the loop. And even more imporatntly, instruct them how to improve it over time - a gift to our future selves. 



## The Experiment

We ran this as a formal experiment with a direct hypothesis:

> If we invest in harness tooling, executable knowledge, and feedback loops, an AI agent can productively modify, build, test, and validate changes to a complex legacy system — and the ROI of that investment pays for itself within the first 3–4 iterations.

In other words: does the harness actually compound value delivery? Or does every session start from scratch regardless?

We measured four things. How hard is the platform for agents today (the difficulty axis). What harness tooling reduces that difficulty (the mitigation axis). How much faster is each successive change (the velocity axis). And — just as importantly — how good is the information we're getting back (the value axis).

The value axis is what makes the whole thing worth doing. Going fast is meaningless if the outputs are shallow. What we actually care about is: are we learning real things about this codebase? Are the architectural questions getting answered with evidence, not guesses? Are the experiments producing findings that change how the team thinks about the platform?

If the harness just made us faster at producing junk, it would be a waste of time. The claim is stronger than that — the harness produces *better* information because it lets us explore more thoroughly, validate from multiple angles (we ran parallel research agents and validation agents against every artifact), and prove things end-to-end against the real running system instead of speculating from code reading alone.
---

## The Start: 16 Hours

The first real task was painful. The agent had to learn the codebase from scratch — understand the architecture, figure out build systems, navigate thousands of files, work out which of the two execution stacks handled which operations.

**First iteration: ~16 hours** to complete a meaningful code change with end-to-end proof.

Here's what happened during those 16 hours: every time the agent hit a problem, we encoded the fix. Not in a wiki. Not in a document. In the harness itself — as a command, a pre-flight check, a recipe.

Every difficulty catalogued became a gift to the next session.

We tracked every one of them. We call it the **difficulty ledger**. Each entry gets an ID (HC-01, HC-02, ...), a category (build, config, data, test, debug, knowledge), and — critically — a mitigation status. The question isn't "did we solve it?" It's "did we encode the solution so nobody ever hits it again?"

By the end: 36 entries. 29 fully mitigated as harness automation. 4 partially mitigated. The ledger itself became one of the most valuable artifacts we produced — a structured record of everything that's hard about this codebase, and what we did about it.

Some examples of what "encoding" looks like in practice. A C# destructor crashes the process silently after garbage collection — only in DEBUG builds, only after a few API calls. An engineer debugging this would lose hours. The harness patches it automatically on build. Nobody ever hits it again. Fresh test databases don't have the new audit columns — the API returns 500 with no useful error. The harness seed command now auto-applies the columns. Every future database works first time. The test framework ships a 32-bit runner that can't load 64-bit test DLLs. The harness wraps a working runner — 29 tests in 5 seconds.

None of these are interesting problems. They're *friction*. But friction compounds just as surely as value does — in the wrong direction. Left unencoded, each one costs the next person hours.

## The Compounding Loop

The second iteration was faster — about 6 hours. But it revealed a new problem: the agent was *forgetting*. It would re-discover things it had already learned. It would try approaches we'd already rejected.

So we locked down the harness concept harder. We created structured knowledge that persisted between sessions — experiment files, design workshops, research dossiers. We gave the harness the ability to tell the agent what it already knew, what had already been tried, and what had already failed.

The third iteration took about 3 hours. The code change was similar in complexity. The difference was the harness — it handled setup, build, deploy, seed, and verification automatically. The agent could focus on the actual problem.

The fourth iteration — 30 minutes. A single line of code to enable, one command to prove it. The fifth — 15 minutes. Zero new difficulties encountered. Zero debugging. Every tool worked first try.

---

## Where It Gets Interesting

By the fourth and fifth iterations, something remarkable happened:

```
Iteration 1:  ~16 hours
Iteration 2:  ~6 hours
Iteration 3:  ~3 hours
Iteration 4:  ~30 minutes
Iteration 5:  ~15 minutes
```

**64× improvement.** Same codebase. Same kind of task. Same agent capability.

The difference was entirely in the harness and the knowledge it carried forward. Each session left the system better than it found it. Not just the code — the *development infrastructure*. The ability to work on the code.

## What Made It Work

Three principles emerged from the experiment.

The first is the compounding value loop. Every task must send a gift to its future self. If you hit a problem, don't just solve it — encode the solution. The agent that runs tomorrow should never hit the same problem you hit today. This is the core mechanism behind the velocity curve.

The second: encode, don't document. But I don't mean build scripts — everyone has build scripts. Here's what's actually different.

The harness has a self-improvement loop. When an agent finishes a task, it produces a retrospective with three fields: what worked, what was confusing, and a "magic wand" — the one thing it would change. The harness's `retro` command reads that retrospective and automatically adds the magic wand to a wishlist. The next agent session reads the wishlist. The harness literally improves itself through use. The agents aren't just users of the tooling — they're the QA team, filing structured improvement requests every time they run. We've had 21 wishlist items flow through this pipeline, most of them resolved.

The other example: the harness doesn't tell you how to test things. It *tests things*. There are full SDK services — invoice, bank transfer, supplier, account — that create real business objects through the API, inject agent identity headers, validate request/response schemas, hit the database to verify the audit trail, and report pass/fail. One command — `just sdk-invoice --agent-id test/1.0` — is a complete end-to-end proof that agent identity flows from an HTTP header through the middleware, through the business logic, into the database. That's not a build script. That's executable knowledge about how a 15-year-old system actually behaves.

The third is rapid experimentation over perfect planning. We ran 6 formal experiments. One was cancelled early (wrong abstraction). Four were confirmed. One is planned. The experiment structure is lightweight — a hypothesis, success criteria, failure criteria, and a go/no-go decision. This let us explore multiple approaches to the same problem and discard bad ideas cheaply.

We used parallel research agents — up to 9 running simultaneously — to explore the codebase from different angles. One traces the inheritance hierarchy. Another checks for double-counting risks. Another reviews prior decisions. They report back structured findings that feed into design workshops. A single engineer looking at a 15-year-old codebase they've never seen would take days to build that mental model. The agents did it in minutes.

## Democratising the Codebase

Legacy codebases accumulate knowledge debt. The people who understand the architecture move on. The remaining team knows their corner but not the whole system. New engineers face a cliff: months of ramp-up before they can contribute meaningfully. Ideas for improvement — even small ones — get stuck in a queue behind "we don't have anyone who knows that part of the code."

The harness breaks this pattern. By encoding operational knowledge — how to build, how to run, where the hooks are, what patterns to follow — we make the codebase *accessible*. Not just to AI agents, but to any engineer who picks it up. The harness is an interface. You don't need to understand everything beneath it. You need six verbs: build, run, health, seed, test, stop.

But the harness alone isn't the full picture. The approach we built around it — structured experiments, parallel research agents, design workshops — creates a new way to explore a codebase.

We can ask architectural questions and get answers fast. Remember the parallel research agents I mentioned earlier — 9 of them, each with a different lens on the same question? That produced 77 structured, numbered findings from a single research session. An engineer doing this manually against an unfamiliar 15-year-old codebase would take days.

We can explore multiple approaches cheaply. Six formal experiments. One cancelled early — wrong abstraction. Four confirmed. One planned. Each with a hypothesis and a go/no-go gate. Bad ideas get discarded in hours, not weeks.

And we captured institutional knowledge at the speed of exploration. 109 workshop documents exploring the system's architecture — not because we needed 109, but because the process was cheap enough to be thorough. Each one captures not just what we decided, but why, and what we rejected. That's institutional knowledge that normally takes years to accumulate, captured in weeks.

This is what "democratising the codebase" actually means. It's not giving everyone commit access. It's giving everyone the *ability to understand* — to explore, to experiment, to ask "what if?" and get a real answer, fast.

## What We Actually Built

To keep this concrete: the exercise was adding audit provenance to the legacy system. When an AI agent creates an invoice or updates a customer record, the system now records *that it was an agent* — which agent, what type, and when. No API contract changes. No service signature changes. Nine files modified in the monolith. Four audit hooks covering two execution stacks. Eight entity types proven end-to-end with real database verification, ~60 more enabled and ready, targeting 80 of 88 total.

But the real deliverable is the capability itself — and not all of it lives in the harness. The harness gives us the ability to stand up the platform locally in minutes with zero cloud dependencies, and to prove or disprove a code change end-to-end in under an hour. That's the harness's job: make the system workable.

The broader approach — parallel research agents, structured experiments, design workshops, validation agents — that's the engineering system we built *around* the harness. This is based on RPI (Research, Plan, Implement - a set of prompts aimed at exploration, engineering and design - a flow as it were.). Those capabilities aren't unique to this codebase. Any team could use parallel agents to explore an unfamiliar architecture, or run structured experiments to compare approaches. What we did is bring those techniques together into a repeatable process and demonstrate that they work against a real, difficult legacy system. The harness makes it practical. The approach makes it valuable. Together, they're something the team can pick up and use — not just on audit provenance, but on whatever question they want to ask next.

The platform didn't get rewritten. It didn't need to be. It got *accessible*.

---

## The Takeaway

The experiment confirmed something we suspected but couldn't prove:

> **Agentic engineering velocity compounds — but only if you invest in the development infrastructure.**

An AI agent without a harness is a fresh graduate staring at a codebase. Every session starts from zero. Every problem is new. Every question takes days.

An AI agent *with* a harness inherits every lesson learned by every agent that came before it. The 34th session is faster than the 1st because 26 problems have already been solved.

For MYOB, this changes what's possible. We don't need to wait for a rewrite to experiment on the platform. We don't need deep tribal knowledge to explore architectural options. We don't need weeks to answer "what if?" The harness gives us the capability to iterate — rapidly, cheaply, and with compounding returns.

The harness is the product. Everything else is the exercise.

## If You Want to Try This

The self-improvement loop I described — agents run, report friction, that friction gets fixed, the next run is smoother — isn't something we built from scratch. It's powered by [minih](https://github.com/AI-Substrate/minih), a standalone agent runner that executes declarative AI agents against GitHub's Copilot SDK.

It's worth distinguishing *minih* agents from Copilot skills (the `/plan-*` commands we used throughout). Skills are valuable — they encode a repeatable process, like "research a codebase" or "write a spec." But skills are static. They're instructions. They don't have opinions about whether the tooling is good or bad, and they don't get better through use. You could prompt each skill to report feedback — but then you're bolting the same concept onto every skill as an afterthought, duplicating something that *minih* bakes in at its core.

*minih* agents are different. They're *users*. They use the harness CLI, hit real friction, and report back what hurt. They're improving their own environment to make things better for themselves. That's the key distinction — a skill tells an agent what to do, but a *minih* agent tells *you* what to fix.

The key idea in *minih* is the **magic wand**. Every agent, after finishing its task, must answer three questions: what worked well, what was confusing, and — the important one — if you could change *one thing* to make your job easier, what would it be? That magic wand is concrete and specific. Not "improve the CLI" but "add a `--viewport mobile` flag to the screenshot command." Not "better error messages" but "when validation fails, include the near-match property name."

What makes this powerful is that agents don't adapt. Humans learn workarounds and stop noticing friction. An agent reports the same problem fresh every single run, until you fix it. And once you fix it, the same agent runs again and validates the fix. The agent is both the user who requested the feature and the QA that tests it shipped.

The compound effect is real. Week 1, magic wands are about missing capabilities — "I can't do X." Week 2, they shift to "I can, but it's awkward." By week 4, they're about edge cases and polish. By week 8, new agents are productive on their first run because the accumulated magic wands have smoothed every rough edge.

You don't need a legacy codebase to benefit from this. Any project with a CLI, a build system, or developer tooling can run *minih* agents against it and start the loop. `npx github:AI-Substrate/minih quickstart` gets you from zero to your first magic wand in about 60 seconds. If you've got something more ambitious — a real project harness, something like what we built — the [RPI framework](https://github.com/AI-Substrate/rpi) gives you the structured planning pipeline (research → specify → clarify → architect → implement → review) that we used to go from "we've never seen this codebase" to "we can modify it in 15 minutes."
